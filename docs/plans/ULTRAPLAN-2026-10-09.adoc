[abstract]
This plan says how to bring `proof-burrower` in line with the hyperpolymath
standards repository and the RSR template format, how to resolve the three open
issues (#105, #104, #84), and which hand-offs go to which bot in which repo.
Companion file: `docs/plans/CROSS-REPO-HANDOFFS-2026-10-09.adoc`.

== 0. Ground rules for executing this plan

* *Plan, not bulk edit.* No A2ML is converted by hand. The retired A2ML files
  move to the deed format only through the family mapping specs in
  `standards/1-formats/deed/mappings/`, using the tooling named there.
* *Normative sources.* Deed grammar: `1-formats/deed/spec/abnf/deed.abnf`
  (v1.1.0). RSR criteria: `0-canon/rsr/rsr-criteria-v2.a2ml` (2.1.0-draft).
  Root shape: template `.machine_readable/root-allow.txt`, checked by
  `scripts/check-root-shape.sh`.
* *Oracle caveat.* The normative RSR oracle, `hypatia:rsr-conformance`, is not
  implemented yet. Every compliance statement below is a repo-local check or a
  file-presence proxy, and is labelled as such.
* *Owner decisions* are listed in section 7 and block the steps that depend on
  them. Nothing in section 7 is decided by this plan.

Rules for the conversion:

* Every family is converted under its own mapping spec in
  `1-formats/deed/mappings/`. The mapping set covers CLADE, META/ECOSYSTEM,
  AGENTIC/NEUROSYM/PLAYBOOK, STATE v1, AI-MANIFEST, and scorecard.
* *Ply has no ruled mapping yet.* The per-directory `0.x-AI-MANIFEST.a2ml`
  files form a ply tree. The template precedent is a `(ply …)` clause in its
  deed (the pilot emitter). Until the standards owners rule, the ply tree is
  left in place and nothing is deleted. (*Gap G-FMT-PLY*, depends on standards R4.)
* The deed for this repo currently has *identity, clade, forges, lineage, status,
  maturity, ecosystem* and lints OK. It is *missing* `rsr-profile`, `meta`,
  `agentic`, `neurosym`, `playbook`, `bot-directives`, `contractiles`,
  `manifest`, `ply`, `anchor`, `ensaid`, `integrations`, `policies`.
  The template deed has all of them and is the worked model.
* Each mapping is applied one family at a time. After each family the repo's
  own gates (`check-no-a2ml`, `validate-rsr`) and the deed lint run. Deletions
  come only after the deed and every reader have been switched.

== 3. Issue-by-issue path

=== 3.1 #105 - combinatorial tactic-playbook synthesis (ParadisEO-mo)

*Status:* open, `enhancement`, updated 2026-10-09. Acceptance criteria:
(a) the swarm synthesises multi-step proofs on benchmark lemmas that fail under
static single-specialist playbooks; (b) intermediate goal caching cuts redundant
prover invocations by at least 40% during local search; (c) full compatibility
with `burrow.jsonl` ledger formats.

*Feasibility, from the code:*

* `TacticTemplate` (`crates/burrower-core/src/attempt.rs:50`) is
  `{name, script, description}`. `generate_probe` builds one
  `lemma probe_lemma: … {script}` per attempt. There is *no multi-step tactic
  AST*, so the neighbourhood operators (swap adjacent steps, substitute premise,
  flip flags) have nothing to operate on yet.
* Step-level delta caching needs a stepwise proof-state interface from ECHIDNA.
  echidna's stepwise surface is *thin*. The FFI `apply_tactic` sends a
  Debug-formatted string and returns a clone of the input state. `verify_proof`
  reads the file text. A proof state is `Term::Var(content)`. So no real
  intermediate goal is available. The CLI has `interactive`, but no contracted
  stepwise protocol exists.
* ParadisEO is C++. The language policy does not allow C++. *Recommendation:
  reimplement the required pieces (tabu, VNS, neighbourhood evaluation) in
  Rust.* No C++ dependency.

*Phased path:*

[cols="1,4,3", options="header"]
|===
| Phase | Work | Exit

| P1 - Tactic AST (Burrower only)
| Define a `TacticScript` as a list of steps for the Isabelle subset that the
  swarm already emits. Add parse/print round-trip tests. Add the three
  neighbourhood operators (swap, premise substitution by signature Jaccard
  distance, flag change) as pure functions.
| Round-trip and operator unit tests pass. No prover calls.

| P2 - Whole-script memoisation (Burrower only)
| Cache results keyed by `hash(lemma, script)`. Count prover invocations with
  and without the cache on the benchmark set. This is an *honest interim*. A
  memo hit requires an exact repeat, so it may not reach 40%.
| Measured invocation counts, reported as they are.

| P3 - Stepwise caching (blocked)
| Needs the ECHIDNA stepwise contract (hand-off E-2 in the companion file).
  Only then can "replay steps 1…k−1 from cache, evaluate from k" be
  implemented.
| Blocked on echidna. Do not fake it.

| P4 - Local search driver
| Tabu/VNS driver in the swarm, with strict attempt bounds and timeouts, and
  a fall-back to manual review.
| Attempt bound and timeout tests pass.

| P5 - Benchmark and acceptance
| Define the benchmark lemma set (lemmas that fail under static playbooks).
  Reuse `docs/experiments/2026-04-26-tropical-comparison/` if it fits (20
  ledger records there). Owner decides the set (D9). Report (a) and (b)
  against it.
| Acceptance (a) and (b) reported with numbers. (b) is marked not met if P3 is still blocked.

| P6 - Ledger compatibility (c)
| Only *additive* optional fields in `LedgerRecord` (`crates/burrower-core/src/ledger.rs`).
  Existing `pattern_kind` values (`positive|anti-pattern|specialisation|boundary`)
  stay. Add a test that reads an old-format ledger unchanged.
| Old ledger fixtures parse. Round-trip test passes.
|===

*Hand-offs:* E-2 (echidna stepwise contract) for P3. The echidna-side
`suggest` JSON contract (E-3) is not needed for #105 and should not be bundled
with it.

=== 3.2 #104 - anti-pattern mining and fitness formulation

*Status:* open, `enhancement`, updated 2026-10-09. Acceptance criteria:
(a) unit tests show known ledger anti-patterns get significant negative fitness
penalties; (b) fitness evaluation under 1 ms per candidate script, in memory,
no live prover call; (c) CLI and socket endpoints follow the existing
line-delimited JSON API.

*Feasibility, from the code:*

* The ledger already has `pattern_kind` and `anti_patterns_for()`
  (`crates/burrower-core/src/ledger.rs:182`). `burrower ledger anti-patterns`
  reports them as text (`crates/burrower-cli/src/main.rs:218`). Reuse them.
* The issue uses `burrow.jsonl`. That file is not tracked in the repo (it is
  produced at runtime by `attempt --ledger burrow.jsonl`). The tracked sample is
  `docs/experiments/2026-04-26-tropical-comparison/ledger.jsonl` (20 records).
  Use the tracked sample for unit tests. Do not commit a live `burrow.jsonl`.
* The socket surface is `burrower serve --socket /tmp/burrower.sock`
  (`crates/burrower-cli/src/main.rs:130–138`; protocol in
  `crates/burrower-core/src/serve.rs`).
* The `GoalReduction` term needs a remaining-sub-goal count from the prover.
  echidna's stepwise path does not provide one (see 3.1). So `GoalReduction`
  is *blocked*.
* The weights w1…w4 are not specified anywhere in the issue. *Decision D10.*

*Phased path:*

[cols="1,4,3", options="header"]
|===
| Phase | Work | Exit

| P1 - Ledger-only terms
| Implement `AntiPatternPenalty` (from `pattern_kind = anti-pattern`
  records, matched by signature/learning), `EstimatedTime` (from recorded
  durations), and `SignatureSimilarity` (token Jaccard, sharing code with the
  indexer). `burrower_core::fitness` module, pure functions.
| Unit tests: anti-pattern fixtures from the tracked ledger get a large
  negative penalty (acceptance a).

| P2 - Latency
| Benchmark the in-memory evaluation (not the CLI process spawn). Target
  under 1 ms per candidate.
| Benchmark result recorded (acceptance b).

| P3 - Surfaces
| `burrower fitness "<goal>" "<tactic_script>"` CLI subcommand. Matching
  socket op in `serve.rs`, following the existing line-delimited JSON.
| Golden JSON tests for both (acceptance c).

| P4 - GoalReduction (blocked)
| Add the term once E-2 (stepwise contract) provides sub-goal counts.
| Blocked on echidna.

| P5 - Mining and calibration
| Mine the ledger for high-frequency failure loops (looping simplifier
  rewrites, diverged inductions). Calibrate w1…w4 with the owner (D10).
| Weights and penalty matrix versioned and documented.
|===

*Hand-offs:* E-2 for P4; B-2 (echidnabot) only if echidnabot is to query fitness.
The issue says "ECHIDNA can query fitness". That is a consumer contract,
which can only follow the socket surface in P3.

  `2-protocols/0-ai-gatekeeper/docs/AI-MANIFEST-SPEC.adoc` still describes ply
  prefixes.

  these statuses are covered only by golden unit tests (no backend without an

  is slower to build than a binding, but no policy exception is assumed.
