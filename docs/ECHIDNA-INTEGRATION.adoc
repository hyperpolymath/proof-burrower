= ECHIDNA + echidnabot Integration Points
:toc: left
:toc-title: Integration map
:sectnums:

How Burrower interoperates with ECHIDNA (the prover-orchestration platform)
and echidnabot (the CI bot that runs ECHIDNA on every push). Three
relationships, three integration surfaces, three concrete edits each side
needs.

This is the dedicated companion to:

* `SWARM-DESIGN-MEANDER.adoc` — *why* the swarm exists
* `AGENT-DSL.adoc` — *how* specialists are defined (in 007)
* `TYPED-WASM-VERIFICATION.adoc` — how Burrower compiles for verification

This doc covers *the wires between Burrower and ECHIDNA / echidnabot*.

== Today (what is wired)

* `echidna prove <file>` — single-shot verification, returns pass/fail
* `echidnabot` — receives push/PR webhooks, dispatches `echidna prove`,
  publishes a check run
* Burrower's `attempt` subcommand subprocess-invokes `echidna prove` for
  each (specialist × tactic) pair, and reads the result through the
  `echidna.prove.result/1` contract when the installed echidna supports it
  (<<prove-result-contract>>)
* EI-1 (`--project-root`) and safe-learning (b) (`--sandbox`) are
  forwarded by `ProverConfig` and asserted on the echidna side. Only the
  Burrower half is checkable from this repository: `prove_command`
  (`attempt.rs`) emits both flags and `process_contract.rs` asserts their
  positions. Whether an installed echidna accepts them is a property of
  that binary, not something proved here.
* BI-1 (`burrower serve`) is implemented on the Burrower side; no echidna
  or echidnabot client calls it yet

The third bullet is the only integration that runs end to end today
(exercised by `tests/e2e.sh` in the `Burrower proof safety` workflow).
Everything else is proposed. Per-item status — implemented, proposed, or
blocked — is in <<status-table>>; do not read a section heading as a
statement that the section is built.

[[topology-invariant]]
=== Topology invariant: no point-to-point ledger wiring

The estate's shared-data-plane model does not permit two repositories to
wire a private channel between themselves, or a repository to open its own
connection to a data store. Two normative statements carry the substance:

* `verisimdb` (`docs/vcl-vs-sql.adoc`): "VCL's **preferred** write path is
  the Octad API (Rust core or Elixir orchestration layer), not the
  language. VeriSimDB treats writes as coordinated multi-modal operations
  that must maintain consistency across all eight modality stores … a bare
  `INSERT` cannot by itself express the cross-modal invariants an octad
  write requires."
* `hyperpolymath/mathesis` (`estate-mathematical-architecture` §8):
  "Agents must not have direct write-access to mutate the canonical
  SQLite index. Provide a strict 'write-back' or 'nomination' API where
  agents can submit discovered broken links, missing verification
  receipts, or false positives for human or CI-gated review."

proof-burrower is an agent in that sentence. Therefore:

. **`ledger::Ledger` is the intended single write point, not an enforced
  guarantee.** The local JSONL file has no lock, so operators must serialise
  all writers that use the same ledger path. It remains the only
  backend that exists.
. **`burrower serve` is a local debugging affordance, not an integration
  surface.** It has no authentication and no peer-credential check; it is
  for an operator on one host. It is not a route for echidna or
  echidnabot to reach the swarm, and no proposal in this document should
  treat it as one.
. **A future non-local backend is an implementation behind `Ledger`**,
  selected by configuration, and for VeriSimDB it goes through VCL / the
  Octad API — never a direct modality-store connection, and never S3,
  which is not a VeriSimDB modality store.
. **Publication to Mathesis is a nomination**, not a write, and it
  carries the fields Mathesis §6 requires (a grade from
  Open / Claimed / Grade 3 / Grade 2i / Grade 2ii / Grade 1, the axiom
  list, and the exact source commit hash of the verification receipt).
. **Receipts cross the seam unchanged and are re-validated on read**
  (<<receipt-on-read>>).

The consequence for the proposals below is that each one names its
adapter rather than its peer: EI-2 consults the ledger, not a socket;
EI-3 nominates, it does not append; EBI-2 configures a backend, it does
not embed an S3 or `vsdb://` client.

[[prove-result-contract]]
== The `echidna.prove.result/1` contract

Shared between echidna (producer), proof-burrower and echidnabot
(consumers). Agreed 2026-10-05.

=== Wire format

`echidna prove ... --output json` prints **exactly one** JCS-canonical
(RFC 8785) I-JSON (RFC 7493) object on stdout, then a newline. Human
output stays the default when `--output` is absent.

[source,json]
----
{"duration_ms":12,"echidna_version":"2.4.0","goal":"probe.thy","message":"","prover":"Isabelle","schema":"echidna.prove.result/1","status":"verified","trust":{"axioms":[],"confidence":null}}
----

[cols="1,1,3"]
|===
|Field |Type |Meaning

|`schema` |string |Always `echidna.prove.result/1`.
|`status` |string |`verified` \| `failed` \| `error` \| `timeout` \| `unknown`.
|`prover` |string |Backend that produced the verdict.
|`goal` |string |The goal or file echidna was asked to prove.
|`duration_ms` |integer |echidna's timing; within ±(2^53−1) per I-JSON.
|`message` |string |Diagnostic; may be empty.
|`trust.confidence` |number or null |`null` unless echidna has a receipt-backed figure.
|`trust.axioms` |array of string |Axioms / escapes the checked proof relies on.
|`echidna_version` |string |Version of the emitting echidna.
|===

=== Consumer rules (proof-burrower)

Implemented in `crates/burrower-core/src/echidna_contract.rs` and
`attempt.rs`.

. **Detection.** Once per echidna binary per process, Burrower runs
  `echidna prove --help` and looks for `--output` as a whole option token.
  Present → contract mode; absent or the binary cannot run → legacy mode.
. **Contract mode.** Burrower appends `--output json` and requires stdout
  to be one line that parses as JSON, equals its own RFC 8785 (JCS)
  canonicalisation byte for byte, names the `/1` schema, and carries every
  field above with the right type. Byte equality also enforces the I-JSON
  limits the parser alone does not: a duplicate key collapses to one
  member and an integer beyond ±(2^53−1) re-serialises differently, so
  both fail as non-canonical. Canonicalisation uses the published
  `serde_json_canonicalizer` crate, because the estate crate
  `hyperpolymath/ijson-jcs` is private and this repository is public (a
  git dependency on it cannot be fetched by CI or by anyone who downloads
  the repo). Switch back once `ijson-jcs` is public or on crates.io. Extra fields are
  tolerated (additive change); removing or retyping a field needs `/2`.
. **Mapping.**
+
[cols="1,2"]
|===
|`status` |Burrower `AttemptResult`

|`verified` + exit 0 |`Succeeded` with a `ProofReceipt` (prover, axioms, confidence, version)
|`verified` + non-zero exit |`Failed` (contract violation: failure evidence wins)
|`failed` |`Failed` with `message`
|`unknown` |`Failed` (inconclusive)
|`timeout` |`Timeout`
|`error` |`Skipped` (infrastructure, no learning recorded)
|malformed / non-canonical |`Failed` (contract violation) — never re-read as text
|===
. **Fallback.** Only when the flag is absent (detection) or clap rejects
  it (`unexpected argument '--output'`, exit 2) does Burrower use the
  legacy text markers (`Proof verified successfully` / `Proof verification
  failed` on either stream, plus the exit code). A legacy success has no
  receipt and the ledger explanation says
  "a warrant, not a receipt".
. **Ledger.** A receipt-backed success stores the receipt under the
  record's `extra.receipt`, including its `result_id` (below).

[[receipt-on-read]]
==== Receipts are validated on the way in, and must be re-validated on the way out

Creation is strict and stays strict: a receipt exists only because
`parse_prove_result` accepted one JCS-canonical line naming `/1`, and only
a `verified` status with a zero exit becomes a success. Nothing in this
document weakens that.

Reading is the weak side, and it is weak *today*: `Ledger::read_all`
deserialises each line and skips malformed ones, but `extra` is an opaque
JSON value, so nothing checks `extra.receipt` before a reader trusts it.
While Burrower is the only writer this is latent. It becomes live the
moment any second writer exists (EI-3, an EBI-2 round trip, a hand-edited
ledger), because a record that merely *looks* receipt-backed would then be
indistinguishable from one that is.

So, before any second ledger writer or non-local backend is added:

* A receipt read from anywhere other than a same-process
  `ProofReceipt::from_result` is a **claim**, not a receipt.
* Re-validate its shape against this contract, and **re-derive
  `result_id`** with `ids::content_id` over the receipt's contract fields.
  A mismatch means the payload changed in storage or in transit.
* A record failing either check is demoted to a warrant — the ledger
  explanation must say so — and the demotion is recorded, never dropped
  silently.

This is `PROOF-POLICY.adoc` §2.1's rule applied to transported evidence:
"Prior `--safe` … successes are historical evidence, not receipts for this
new combined profile."

The receipt/warrant split follows the factive/non-factive distinction in
`hyperpolymath/epistemic-types` (`FactiveModality`, with real Kripke
semantics as of `5422cd5`). It is copied as a pattern; Burrower does not
depend on that Agda library and must not start to.

[[identifiers]]
=== Identifiers

All identifier minting lives in `crates/burrower-core/src/ids.rs`; nothing
else in the workspace mints an id. The policy (owner, 2026-10-05) is v7 for
things that happened and v8 for things that are:

[cols="1,1,2"]
|===
|Function |Kind |Used for

|`ids::new_record_id()` |UUIDv7 (RFC 9562 §5.7, `uuid` crate API)
|Ledger record `id` (via `ledger::new_id`, a thin alias). Writers:
 `attempt::run_playbook`, `oracle::record_to_ledger`, `ledger::record_reading`.
|`ids::content_id(value)` |UUIDv8 (RFC 9562 §5.8 / Appendix B.2)
|SHA-256 over the JCS bytes of `value`, first 16 bytes, version nibble `8`,
 variant `10`. Same JSON content -> same id.
|`ids::goal_content_id(text)` |UUIDv8 |Ledger `goal_id` (content id of the
 goal text as a JSON string).
|`ProofReceipt::from_result` |UUIDv8 |Receipt `result_id`: content id of
 the prove result's contract fields.
|===

`goal_hash` (16 hex chars, non-cryptographic) is kept unchanged because the
wasm ABI (`goal_hash_hex`, 16-byte buffer) and existing ledgers depend on
it. Ledgers written before this change carry no `goal_id`; the field is
optional on read. Record ids before this change were `<millis>-<seq>`
strings, not UUIDs; old ledgers keep them.

Not yet content-addressed: corpus entries (`corpus::IndexedLemma`) carry no
id today; when they gain one it must come from `ids::content_id`.

The receipt/warrant vocabulary is defined in <<receipt-on-read>>.

[[grading]]
==== What a receipt must carry to be indexed by Mathesis

The estate grades proofs rather than scoring them.
`hyperpolymath/mathesis` (`estate-mathematical-architecture` §5, §6)
requires that a result be recorded as exactly one of *Open, Claimed,
Grade 3, Grade 2i, Grade 2ii, Grade 1* — "Do not flatten proof confidence
into a percentage" — together with its axiom dependencies and "the exact
Git commit hash of the verification receipt", plus `Superseded` and
`Regressed` statuses for results that stop holding.

`ProofReceipt` today carries `schema`, `prover`, `axioms`, `confidence`,
`echidna_version` and `result_id`. Against that requirement it is short:

[cols="1,3"]
|===
|Missing |Why it matters

|a *grade*
|Without one, a Burrower success has no place on the ladder, and
 `confidence` becomes the de facto grade — the flattening §6 forbids.

|a *source commit hash*
|`echidna_version` is a version string. The one commit pin this repository
 actually holds is in `.github/workflows/proof-safety.yml`
 (`556d6468…`), and it never reaches the receipt, so a receipt cannot be
 tied to the code that produced it.

|*stdlib / toolchain pins*
|`PROOF-POLICY.adoc` §2.1: "Pin and record the Agda version and standard
 library with each source commit and proof result."

|*axiom dispositions*
|`trust.axioms` lists escapes but does not classify them. The estate
 requires each to be (a) DISCHARGED, (b) BUDGETED with a refutation
 budget, or (c) a NECESSARY AXIOM with a justification
 (`docs/TRUSTED-BASE-REDUCTION-POLICY.adoc`). An unclassified axiom is the
 unfalsifiable "covered by tests" that policy rejects.
|===

These are **not** added to `/1`. Removing or retyping a field needs `/2`,
and so does adding semantics to an existing one; the grade and commit
fields belong in `echidna.prove.result/2` (hand-off E-1/T-2 in
`docs/plans/CROSS-REPO-HANDOFFS-2026-10-09.adoc`). Until then Burrower
records what echidna reported and asserts no grade of its own — its
Isabelle results sit on the estate's Engineering Path, and Grade 1
requires the verified-checker-API route, which is echidna's property.

=== Tests

* `echidna_contract::tests` — canonical parse, every status, planted
  non-canonical mutants (key order, whitespace), empty / multi-line /
  duplicate-key / unsafe-integer / wrong-schema / wrong-shape rejection.
* `ids::tests` — same JCS content gives the same v8 id; the v8 id is the
  SHA-256 prefix with exactly the version/variant bits changed; v7 record
  ids carry version 7 and sort in minting order.
* `attempt::tests` — fake echidna binaries for the contract path (every
  status, receipt transport into the ledger), a malformed-output liar, the
  legacy path, and a binary that advertises the flag but rejects it.
* `tests/e2e.sh` (CI `Burrower proof safety`) — real Isabelle through the
  echidna pinned in `.github/workflows/proof-safety.yml`. That pin predates
  the contract, so today this exercises the **legacy** path; bump the pin
  once echidna ships `--output json` to exercise the contract path live.

[[corpus-overlap]]
== Overlap with echidna's corpus subsystem (recommendation)

echidna ships `echidna corpus ingest|query|stats|crossquery|near|
export-octads` over 20 prover adapters (Agda, Coq, Lean, Isabelle, Idris2,
Mizar, Metamath, HOL4, HOL Light, ACL2, TPTP, SMT-LIB, Why3, F*, Dafny,
MiniF2F, ProofNet, ...), with dependency closure, a cross-prover synonym
table, and hashing-trick vector embeddings (`near`, cosine similarity).

Burrower's `corpus` + `ranking` index `.thy` / `.v` / `.lean` and rank by
Jaccard over signature tokens. Overlap is real: both build an inverted
index of lemma signatures and answer "what is near this goal".

What only Burrower has: the specialist swarm (per-vocabulary readings,
consensus homes, boundary objects), tactic playbooks, the attempt loop and
the ledger.

**Recommendation.** Do not grow Burrower's own indexer further. Keep it as
the zero-dependency fallback (it powers the WASM shim and runs without
echidna), and add an optional retrieval backend that shells out to
`echidna corpus near --format json` when echidna is present, so specialists
rank echidna's richer candidates. That needs a stable JSON contract for
`corpus near` analogous to `echidna.prove.result/1`; until echidna defines
one, the two indexers stay separate. Not implemented in this change.

== ECHIDNA — three concrete changes

=== EI-1 (small): project-aware probe

**Problem.** `echidna prove <file>` stages the file in `/tmp/echidna_*/`
without copying sibling theory files, so any goal that imports
project-specific theories (`Tropical_v2`, `walks_def`, ...) fails to
parse. Burrower's `attempt` mode therefore can only test goals that
import `Main` only — a severe limitation.

**Fix.** Add a `--project-root <dir>` flag (or auto-detect a `ROOT` file
walking upward from the supplied path). When set, ECHIDNA stages the
file *together with* the project's session — either by copying the
relevant theories or by running `isabelle build -D <root> -v <session>`
and capturing per-theory results.

**Acceptance test.**
[source,bash]
----
echidna prove --prover Isabelle --project-root . \
  verification-ecosystem/tropical-resource-typing/Tropical_Ordinal.thy
# expect: Proof verified, all 15 lemmas, ~3s
----
Currently fails because `Tropical_v2` import isn't carried.

**Burrower side.** `crates/burrower-core/src/attempt.rs::run_probe`
gains a `project_root: Option<PathBuf>` field on `ProverConfig`. Probe
generation can stop inlining `imports Main` and use the project's
imports verbatim.

=== EI-2 (medium): `echidna suggest` subcommand

**Problem.** When `echidna prove` returns red, the user sees only
"failed". No suggested fix, no related lemmas, no tactic alternatives.
The `--diagnose` flag prints generic advice ("try a smaller example").

**Fix.** New top-level subcommand:
[source]
----
echidna suggest <file>:<lemma> [--budget 60s] [--ledger <burrow-ledger>]
----

Behavior:

. Extract the lemma's statement into a probe.
. Run Sledgehammer for `--budget` seconds (Isabelle has this built-in).
. **If `--ledger` is provided**, read the Burrow ledger for ranked
  candidate homes + anti-patterns. Format as additional suggestions. This
  is a *read* of a shared artefact, not a call into a running Burrower:
  per <<topology-invariant>> echidna must not dial a Burrower socket, and
  the earlier `--burrower <socket>` form of this flag is withdrawn.
. Try a curated list of *substitutions* (the synonym table from
  `AI-WORK-echidna.md` §3.2): `induct→induction`,
  `add_le_add→add_mono`, `omega→linarith`, `by simp ↔ by auto`, etc.
. Report which variants closed.

**Why this matters.** This session's two ECHIDNA-discovered fixes
(`induct → induction`, `add_le_add → add_mono`) would have come for
free from the substitution loop. The Burrower hits (e.g., the
`tropm_walks_sum_mono_subset` dual lemma pointer) would surface as
"see also" recommendations.

**Implementation sketch.**
[source]
----
echidna/src/rust/main.rs                 # add Suggest variant to Cli
echidna/src/rust/suggest/mod.rs          # new module
echidna/src/rust/suggest/synonyms.toml   # the curated substitution table
echidna/src/rust/suggest/burrower.rs     # optional client to Burrower socket
----

=== EI-3 (large): native ledger consumer

**Problem.** When ECHIDNA fails to close a goal, that failure isn't
recorded anywhere reusable. The next time someone tries the same goal,
ECHIDNA repeats the same exhaustive search.

**Fix.** ECHIDNA gains a Burrow-Ledger *nominator*: every prove
invocation produces a `LedgerRecord` (matching the schema in
`crates/burrower-core/src/ledger.rs`) and submits it to the shared ledger
layer. It does not append to a Burrower-owned file directly.

The distinction is load-bearing, not stylistic. `ledger.rs` documents
"One writer; many readers" and "No locking yet — single-writer assumed",
so a second process appending to the same path is both a data race and a
way to manufacture records that look receipt-backed without a receipt
(<<receipt-on-read>>). Mathesis §8 states the rule for the estate: agents
"must not have direct write-access to mutate the canonical … index" and
instead submit through a "write-back" or "nomination" API gated by a human
or CI. An echidna-produced record therefore enters as a nomination that
the ledger owner validates — re-deriving `result_id` where a receipt is
claimed — before it counts.

Successful proofs become positive patterns; failures become anti-patterns
or generic-failures.

Configuration:
[source,toml]
----
# ~/.config/echidna/config.toml
[ledger]
nominate_to = "burrow"        # ledger layer, not a file path
auto_nominate = true
specialist_name = "Echidna"   # appears in the ledger as the author
----

**Why this matters.** ECHIDNA becomes a first-class participant in the
swarm's shared knowledge layer rather than an opaque external prover.
Other specialists in the swarm can read ECHIDNA's track record and
update their playbooks.

== echidnabot — three concrete changes

=== EBI-1 (small): swarm-findings section in PR comments

**Problem.** echidnabot's PR comments today say "✓ all proofs
verified" or "✗ proof X failed at line Y". No domain context, no
related-work pointer, no anti-pattern callout.

**Fix.** echidnabot invokes `burrower swarm` as a subprocess for every
new/changed lemma and includes the synthesis output in the PR comment as
a collapsed "Swarm findings" section. This is the same shape as its
existing `echidna prove` dispatch — a CLI call, not a connection — so it
needs no socket and stays inside <<topology-invariant>>. Reading the
anti-patterns from a shared ledger goes through that ledger's backend,
not through a live Burrower process.

Example PR comment delta:
[source,markdown]
----
✓ Proof verified: trop_walks_sum_mono_subset (line 720, 33ms)

<details>
<summary>🦔 Swarm findings (3 specialists engaged)</summary>

**Boundary object** across Combinatorics, Order Theory, Algebra.

Consensus homes:
- `trop_walks_sum_ge_member` (cited by all 3)
- `tropm_walks_sum_mono_subset` (min-plus dual — port pattern available)

Algebraist anti-pattern (most-recent ledger): `simp` known to fail on
this shape; auto succeeds (3 prior runs).

</details>
----

**Implementation surface.** `bots/echidnabot/src/feedback/swarm.rs`
(new). Plumbed from the post-verification hook.

=== EBI-2 (medium): ledger as first-class CI artifact

**Problem.** The Burrow Ledger is a local-disk JSONL today. CI runs
should contribute to a shared, persistent ledger so knowledge accumulates
across PRs and over time.

**Fix.** echidnabot nominates the per-PR ledger delta to the shared ledger
layer. The full repo ledger is reconstructible from the deltas. New PRs
can read the historical ledger to surface anti-patterns from prior similar
work.

The earlier form of this item offered `backend = "verisimdb"  # or "s3"`
with a `vsdb://swarm/burrow-ledger` URL. That is withdrawn: it is a
point-to-point client from CI into a data store, which
<<topology-invariant>> rules out, and "or s3" offered an uncontrolled
bypass as a peer option even though S3 is not a VeriSimDB modality store.
A delta reaches VeriSimDB through the Octad API (`POST /api/octads`),
which is what `verisimdb/docs/vcl-vs-sql.adoc` names as the preferred
write path, because a bare write "cannot by itself express the cross-modal
invariants an octad write requires".

What this needs from Burrower first, in order:

. the `LedgerBackend` seam, with the local JSONL file as its only
   implemented backend;
. read-path receipt re-validation (<<receipt-on-read>>), because a delta
   that has been uploaded and downloaded is exactly the case where a
   receipt can arrive altered;
. resolution of whether `verisimdb-client` can be depended on from this
   public repository, and whether `burrower-core` gains an async runtime
   or a blocking bridge to talk to it.

Schema (TOML), backend named by kind rather than by endpoint, so no URL or
credential ever appears in repo config:
[source,toml]
----
[ledger.storage]
backend = "local"        # the only implemented backend today

[ledger.delta]
nominate_on = ["pr-merged", "main-push"]
delta_only  = true       # nominate the delta, not the whole ledger
----

=== EBI-3 (large): ECHIDNA-failure → swarm-remediation auto-PR

**Problem.** When ECHIDNA finds a real proof failure on `main`, the
fix has to be done manually. Even if the swarm's ledger contains a
known-good substitution (e.g. `induct → induction`), echidnabot
doesn't propose it.

**Fix.** echidnabot gains a "remediation mode": on a verified ECHIDNA
failure, query the swarm + ledger for known good fixes; if the evidence
meets the bar, auto-open a PR with the suggested edit. PR description
cites the ledger evidence.

**The bar is a grade, not a percentage.** The earlier form of this item
set a numeric "Confidence threshold … defaults to **0.8** (i.e., fix is
known to have worked on 4 out of 5 prior similar goals)". That is
withdrawn on two estate grounds: Mathesis §6 — "Do not flatten proof
confidence into a percentage. Record exactly whether a result is Open,
Claimed, Grade 3, Grade 2i/ii, or Grade 1" — and §13 — "Do not allow
agent-generated evidence to count as independent corroboration". A tally
of prior swarm successes is agent-generated evidence about *other* goals;
it is not corroboration for this one, and no threshold on it makes it so.

Replacement rule: a remediation PR may be opened only where the suggested
edit rests on a ledger record that is **receipt-backed** — a
`ProofReceipt` whose `result_id` re-derives (<<receipt-on-read>>) — for a
goal whose content id matches under the corpus's own similarity, with the
matching stated in the PR body. Anything weaker, including any count of
prior similar successes, is posted as a comment-only suggestion and
labelled as unverified.

Operational policy: PR labels include `swarm-suggested` so reviewers
can filter; auto-PR rate-limited per repo per day.

== Burrower side — three reciprocal hooks

=== BI-1 (small): expose `burrower serve` socket — *implemented*

**Implemented** in `crates/burrower-core/src/serve.rs`: `burrower serve
--socket /tmp/burrower.sock` listens on a Unix socket, one thread per
connection, and refuses to bind an occupied path.

Protocol: simple line-delimited JSON (request: `{cmd, args}`,
response: same as the CLI's `--format json` output), with
`cmd` ∈ `swarm | attempt | ledger | ping`.

**What it is not.** It has no authentication and no peer-credential
check, and nothing in the estate calls it. It is a local debugging
affordance for an operator on one host — not the integration surface for
echidna or echidnabot, which reach Burrower through the CLI and the shared
ledger instead (<<topology-invariant>>). The earlier text here said
"ECHIDNA's `--burrower` flag and echidnabot's swarm-findings hook both
consume this socket"; that intent is withdrawn. Making it a real service
surface would need authentication, a peer-credential or token check, and a
decision on multi-request streams, none of which exists.

=== BI-2 (medium): ECHIDNA-as-specialist

**Today.** Burrower's specialists are pure Rust types.

**Fix.** Add an `EchidnaSpecialist` that, given a goal, dispatches
through `echidna prove` rather than running its own playbook. Lets
the swarm treat ECHIDNA as just another agent — competing with
Algebraist / OrderTheorist / Combinatorialist on every goal.

Why valuable: gives a baseline (ECHIDNA is the strongest single
prover) so the other specialists' contribution is measurable as
*marginal* over the baseline.

=== BI-3 (large): bidirectional ledger sync

**Today.** Burrower writes its own ledger. ECHIDNA writes its own
(after EI-3).

**Fix.** Both contribute to the *same* ledger through the shared ledger
layer, with `ledger::Ledger` as the single in-process write point and
echidna contributing by nomination (EI-3). ECHIDNA shows up as one
specialist among many in the digest.

The earlier form — "Both write to the *same* ledger via a shared socket"
— is withdrawn. It was point-to-point by construction, and it made a
second process a writer of a file that `ledger.rs` documents as
single-writer with no locking. A socket is a transport between two
peers; what is actually needed is one ledger with one writer and a
gated path in for everyone else.

== Open questions

. Should the Burrow Ledger be one global file per estate, or one per
  repo? Probably per-repo with a global digest layer, but TBD.
. Should ECHIDNA's `suggest` learn from the ledger to *order* its
  Sledgehammer attempts (cheap-tactic-first based on prior success
  rates)? Probably yes; out of scope for v1 of EI-2.
. Should echidnabot's auto-remediation PRs be opt-in per-repo? Almost
  certainly yes — the blast radius of an auto-edit on main is huge.
  Default to off; require explicit `[swarm.auto_remediate] = true` in
  echidnabot's repo config.
